Ongoing Project
Code

On tasks of the trained types, multi-turn agent SFT takes the 4B model from 16.7% to 87.3%, past the official Qwen3.5-4B (57.7%). On FinSearchComp tasks written outside the project it reaches 74.5%, past the official model's 64.3%, and on long-document QA it reaches 53.0%, level with the official model.

Abstract

This project post-trains a 4B base model, Qwen3.5-4B-Base, into a tool-using financial agent that looks up market prices, macroeconomic series and company filings, computes over them in a Python sandbox and answers multi-step questions. The official post-trained Qwen3.5-4B already solves 84.7% of our earlier market-retrieval development tasks, so we built a harder offline dataset of 3,148 tasks (2,350 training, 200 development and 598 test tasks). Of these, 2,850 are generated in the style of the public benchmark FinSearchComp over a fixed data snapshot, with answers computed by programs and rechecked by an independent implementation; the rest are 98 FinSearchComp tasks and 200 DocFinQA questions over full annual reports. A teacher, the larger model Qwen3.8-27B, solves the market training tasks of two difficulty tiers and tasks that read annual reports inside an agent harness, the code that gives a model its tools and checks its answers, and each attempt is saved as a trajectory, the full record of its messages, tool calls and tool results. These trajectories, after filtering, with filtered wealth-management and machine-learning trajectories and 2,000 samples from a 1:1 mix of finance and general data, train the 4B model with multi-turn agent SFT (supervised fine-tuning, which continues training on examples with known answers). On 300 market-data test tasks from held-out stocks and later periods, the SFT model solves 87.3%, against 57.7% for the official Qwen3.5-4B, 16.7% for the base model and 94.7% for the teacher. On DocFinQA it solves 53.0%, level with the official model and 14.0 points above the first SFT run, whose data held no trajectory that read a report. The project uses DAPO for reinforcement learning from the SFT checkpoint. These reported SFT results belong to the earlier data batches; the data architecture below separates programmatic expansion from Claude exploration and applies common review.

The data architecture combines programmatic generation for known weaknesses with Claude generation for uncovered task structures. Both branches pass the same independent checks and mandatory Claude review. Task approval, demonstration approval and measured training gains are separate questions.

Fixed sources and four splits keep selection separate from final testing

  • Source inventory: Each task records its source snapshot, entities, dates, parent, task family and generation method. Question overlap and report overlap are counted separately, so a new question on a seen report is not presented as a new report.
  • Four-way split: Training supplies examples, calibration fixes formats and difficulty measurements, development selects mixtures and checkpoints, and a frozen test set reports the final choice. Related tasks inherit their source split; test questions and answers never enter the generation feedback.
  • Failure analysis: Valid failures on training and calibration tasks identify missing operations, unstable decisions and uncovered constraints. Tool failures and malformed questions are diagnosed separately so generation does not turn infrastructure errors into harder exercises.

Two branches practise known weaknesses and explore missing task structures

  • Program generation + Claude review: Seeded programs vary entities, dates, constraints and dependent operations inside verified task families. This branch supplies reproducible practice where the model is inconsistent or repeatedly fails a valid task, and also supplies simpler intermediate exercises.
  • Claude generation + Claude review: A generation conversation receives a capability gap, available data and tool contracts, and proposes a task family and instances with explicit rules. Rewording an existing question or adding text does not count as new capability coverage.
  • Trusted task adapters: An adapter maps a structured task into tool execution and an independent answer computation. The market adapter handles price windows, offsetting market exposure and costed holdings; bounded integer allocation states how many lots each account may buy under its own limits and a shared budget. Unsupported proposals stay isolated until their data, tools and validators are established; generated validator code is not trusted by default.
  • Family promotion: A Claude-origin family can become a verified program template for repeated expansion. Its original designer and each instance's current generator remain separate provenance fields, and every new instance still passes common review.

Independent computation and Claude review check different failure modes

  • Rules and tool execution: Schema, units, duplicates and split boundaries are checked before model review. Separate computation implementations recompute the reference, and a reference solution runs through the actual tools, so an executable answer cannot rely on inaccessible evidence.
  • Blind solution: A fresh Claude conversation sees only the student-visible question, materials and tool contract, and writes a solution. The solution executes in the same CPU tool sandbox and its output must pass independent grading before adversarial review.
  • Adversarial review: Another fresh conversation checks the question and reference for ambiguity, contradictions, unavailable information, wrong units, future information and grading exploits. Every retained instance needs a reasoned approval; missing, failed or over-budget reviews remain unresolved. Separate conversations do not guarantee independent errors.

Measured success patterns route tasks to different training uses

  • SFT candidates: A successful teacher attempt is a candidate demonstration, not automatic admission. Only a trajectory that passes its own checks and review enters supervised fine-tuning, which teaches the model by imitation.
  • Demonstration review: Each retained SFT trajectory additionally needs successful evidence reads, valid calculations, an accepted terminal answer and Claude review of the actual method. Tokens of rejected actions remain in context but are excluded from the imitation loss, so a successful recovery need not teach the rejected action.
  • RL candidates: Tasks with both correct and incorrect current-student attempts can supply within-group reward differences for DAPO. All-wrong tasks first receive diagnosis, reliable demonstrations or intermediate exercises; all-right tasks can serve retention. Finite attempts estimate current performance, not learning gains.
  • Deduplication and reuse: Exact questions and related source instances are checked across training and reserved pools. A fresh RL pool excludes questions used in the preceding SFT batch; online RL rewards remain programmatic rather than adding a Claude judge to every exploration trajectory.

Mixing counts approved instances and releases immutable training inputs

  • Accepted-instance mixture: Branch proportions count unique questions that pass the shared review, not generation attempts or multiple trajectories of one question. A shortfall stops publication rather than silently filling the quota with duplicates or rejected tasks. SFT tokens and effective RL groups are reported separately.
  • Cost control: Rules reject obvious failures first, and exact version-bound reviews can use a cache. Accounting includes Claude generation, both branches' task reviews, SFT trajectory reviews and failed attempts. A shared cap reserves the worst-case request cost before sending, and interrupted or unpriced calls block further spending.
  • Release contract: Code, snapshots, prompts, model identities, independent references, reviews, task IDs, tokenizer and loss masks are bound to the released data. CPU diagnostic readiness and simulation outputs cannot authorize training. Fresh SFT starts from the Base checkpoint with a new packed dataset and output directory; RL follows the resulting checkpoint and fresh difficulty measurements.

The reported model's original program-generated task collection uses fixed snapshots and executable reference answers.

The data snapshot fixes the data, so programs can compute and recheck every answer

  • SQLite snapshot: One database file stores daily prices of 565 securities with 35,727 splits and dividends, 68 FRED macroeconomic series and the SEC XBRL filings of 516 companies (machine-readable company financial reports). Live data would change, so only a fixed snapshot lets a program compute each answer and grade each task.
  • Point-in-time vintage: The snapshot fixes FRED values at its cutoff or latest stored vintage; it does not reconstruct what was known at every earlier decision date, so these tasks do not establish historically available-information backtests.

The split keeps test entities and periods out of training

  • Entity split: A hash of the ticker assigns each stock to training, development or test at about 70/10/20, and filing tasks follow their company, so the market-data test measures companies the model has not seen.
  • Temporal split: Indices, ETFs (funds that trade like stocks), FX rates and FRED series split by time into 2000–2016 for training, 2017–2019 for development and 2020 onward for test, so the market-data test measures periods after the training window.
  • Limit of the split: The development set holds 47 stocks and the test set 99, and the S&P 500 list comes from 2026, so it holds only companies that survived to that year.

The original program-generated batch follows FinSearchComp and adds a hard tier

  • Need for harder tasks: The official Qwen3.5-4B already scores near full marks on 11 of the 14 wealth-management task types, which mainly test calling tools by the rules, so the project needs tasks the official model also does badly on.
  • Operations from FinSearchComp: Labelling FinSearchComp's T2 and T3 tasks showed recurring operations, such as unadjusted prices, the Nth trading day after a date, threshold scans, period extremes, monthly resampling, maximum drawdown and rolling standard deviation, and the generator builds task types from them because the benchmark's difficulty comes from many periods of data, price adjustment, unit conversion and multi-step aggregation.
  • Original tier: The generator builds 17 task types of difficulty 1–3 by drawing entities and time windows, with 200 training, 20 development and 30 test tasks per task type, so training practices each of the operations above on its own.
  • Hard tier: The generator builds 8 composite task types of difficulty 4–5, motivated by the teacher solving 99.7% of original-tier development tasks; the student's RL signal still needs its own measurement. A composite task chains operations, so one wrong step fails it, and difficulty comes from steps and conventions, not obscure data.
  • One round of hardening: The generator rewrites the 5 hard task types on which the teacher scores at least 95% on the development set, giving company names only, standard terms and extra keys, which lowers the teacher from 98/100 to 93/100 on them, because the tier needs tasks the teacher can also get wrong. This happens once, because repeated changes would tune the tasks on the development set.

Answer computation gives every task a reference a program can check

  • Computed answers: The generator computes each reference answer from the snapshot and drops candidates that invite misgrading, such as answers near a rounding boundary or dates close to a threshold, so a score does not turn on a rounding edge.
  • Key-based grading: The grader splits a reference answer into keys (a number within tolerance, a date, a text or a set) and passes a task only when every key appears correctly in the final answer, so scores need no model judge and can be recomputed. A count key can still match another small integer in the answer.

Independent verification checks answers and tools

  • Independent verification: A separate SQL and Python implementation recomputes answers from task parameters; all answers in both tiers match. Comparing implementations can expose discrepancies, but shared assumptions or mistakes can still escape this check.
  • Golden policy: A scripted solver uses only the tools, one Python call and finish, and solves every task through the same loop, verification and grading as the model, which shows the tools are sufficient for each task.

The dataset holds 3,148 tasks, with sources and task types chosen on development results

  • Composition: The dataset fixes 2,350 training, 200 development and 598 test tasks, totaling 3,148. The Data section lists the test sources. Development guides method selection; the frozen test reports the selected method.
  • Training file: The file holds 250 tasks from each of 7 hard task types and 200 from each of rolling_vol, extreme_period and xbrl_ratio, 2,350 tasks in all. It drops the eighth hard type, div_event_study, because the official model solves 19/20 of its development tasks, which leaves no room to show a gain, and it keeps the original tier's three types the official model does worst on (2/20, 14/20, 14/20). The SFT model also uses trajectories on the other 14 original-tier task types, 2,800 tasks beyond these.
  • Development and market-data test files: Both files use the same task types under the entity and time splits above. Test tasks are not selected by whether a model answers them correctly, so models can be compared on the same fixed questions.
  • FinSearchComp file: Of the 203 Global T2 and T3 tasks, the file keeps the 98 on which the snapshot's value agrees with the official answer within tolerance, so a score does not rest on a snapshot value that disagrees with that answer.
Context management Tool interface and constraints Verification and correction

The harness in this work has three parts: context management, tool interface and constraints, and verification and correction. The description below is version 3, used on market and DocFinQA tasks; wealth-management, machine-learning and t6_report_gate tasks use version 2, which truncates older tool results into summaries.

Context management

  • System prompt: The harness opens each task with a message that states the model's role, the task's rules and how to use the tools.
  • Append-only context: The harness never changes a message after sending it, so each request's messages are a prefix of the next request and of the stored trajectory. The stored trajectory is then exactly what the model saw at each step, and SFT and RL train on the sequence as it was sampled.
  • Tool-result cap: The harness cuts each tool result to 8,000 characters when the tool returns it and appends a note on how to ask for less, such as the next page or a shorter date range. Every market tool returns at most 7,500 characters per page and read_chunk with neighbouring passages about 7,100, below the cap, so the model does not receive cut-off JSON.
  • Checklist (set_checklist): The model writes the steps of a request into a checklist and marks them done, the harness restates the list after every tool result, and the model may call the tool at most 20 times in a task. This mainly reduces skipped sub-tasks.
  • Step budget: The harness counts only task turns against the limit of 100 steps; checklist-only turns, a turn with a rejected finish and the 10 turns after it stay outside the count, under a hard cap of 142 turns. Checklist upkeep and redoing are actions the harness itself adds, and on long tasks they would use up the step limit.
  • Thinking-preserving chat template: A changed Qwen3.5 chat template, the rule that renders messages into model input, keeps the thinking of every assistant turn after the first user message. Under the original template a nudge, which is a user message, removed the earlier thinking from the next prompt, so the stored trajectory was no longer what the model saw.
  • Token-level logging: The harness records each turn's prompt token count, sampled tokens and their log probabilities, plus prefix_ok, a flag for whether the prompt begins with the previous prompt and its completion. RL can then use the sampled tokens and probabilities without rescoring them, and the flag exposes any turn rendered differently from how it was sampled.

Tool interface and constraints

  • Function calling: The harness describes each tool's name and arguments to the model in JSON Schema, a standard format for structured data, and the model calls tools in the native function-calling format.
  • Tool sets: The market environment offers 11 tools, wealth management 12, machine learning 5, DocFinQA 4 and t6_report_gate (version 2) 14, each count including finish, which ends a task with the answer; the full harness adds set_checklist.
  • BM25 two-step retrieval: BM25, a keyword ranking algorithm, scores a passage higher when the query's words are frequent in it and rare elsewhere, and the harness uses it alone, with no vector search or reranking. A search of the wealth-management knowledge base of fund prospectuses returns ids, titles and opening text of at most 10 passages, and the model then reads a full passage by its id. DocFinQA cuts a 10-K into passages of 1,500 characters with 200 characters of overlap, a search there returns snippets of about 240 characters, and only read_chunk gives the full passage.
  • Sandbox (run_python): The harness runs the model's code in bubblewrap, a Linux tool that isolates a process, with no network, a read-only file system outside a temporary directory, 30 seconds and 3 GiB.
  • Constraints: Before a write action runs, code checks its arguments against the tool schema and the business rules, refuses a violating action unexecuted and returns the reason to the model, which mainly reduces rule violations and bad arguments.

Verification and correction

  • Answer verification: On finish, the harness checks that the answer's numbers have support in tool results or the request, that every checklist item is done and that the environment's own checks pass; on market tasks a number counts as supported when a tool-result number matches it after scaling by thousands, millions, billions or percent and rounding to the answer's decimals. Unit conversions therefore pass, while numbers worked out in the model's head or recalled from memory are rejected.
  • Rejection limit: The harness rejects at most 2 finishes in a task and accepts the next one unchecked.
  • Correction messages: The harness returns the failing checks after a rejected finish and an example of a valid call after a tool error, which mainly reduces loops and exhausted step budgets.
  • Loop hint: The harness tells the model to change approach on the third identical call.
  • Nudge: The harness appends a reminder after a reply with no tool call.
  • Packing: The builder drops 48 trajectories over their token limits and 7 multi-user-message trajectories that would lose earlier thinking under the chat template. It renders market and DocFinQA trajectories with the thinking-preserving chat template up to 32,768 tokens, and t6_report_gate trajectories up to 32,768 and wealth-management and machine-learning trajectories up to 16,384 with Qwen3.5's own template, then packs the 14,486 samples into 2,830 sequences of at most 32,768 tokens, so short samples fill each sequence's token budget and a step of 12 sequences trains on about 61 samples. The market limit is 32,768 because the median xbrl_ratio trajectory has 17,661 tokens, so 16,384 would lose over half of that task type.
  • Settings: Training fine-tunes all parameters of Qwen3.5-4B-Base for 2 epochs (two passes through the data) and 472 steps, on 6 GPUs, at a learning rate of 1e-5 that falls along a cosine curve. It starts from the Base model so that everything the model learns after pre-training comes only from this project's data.
  • Loss: Training minimizes the cross-entropy between the model's next-token prediction and the label, the standard loss for next-token prediction \(\mathcal{L} = -\frac{1}{N}\sum_{t:\, y_t \neq -100} \log p_\theta(y_t \mid x_{<t})\), where \(x_{<t}\) is the sequence before position \(t\), \(\theta\) the model weights and \(N\) the number of labeled tokens, so the model reproduces the labeled turns token by token. Training computes the loss only at labeled positions, in chunks, which leaves its value and gradients unchanged, because the model's scores for every vocabulary token at every position of a long sequence do not fit in GPU memory.
  • Labels: A label is the token itself where the model should learn and −100, which the loss ignores, everywhere else. The labels cover thinking, text and tool calls in a trajectory's assistant turns, because the model later runs under a chat template that keeps past thinking in its context, and they mask system, user and tool turns, because tools produce their own output.
  • Masked turns: Market and DocFinQA trajectories mask a reply that drew a nudge and a turn with a rejected call but keep them in the context, because a loss there would teach the model to hand in wrong answers first, while the later correction is still learned; t6_report_gate trajectories mask rejected turns too. Wealth-management and machine-learning trajectories keep the loss on rejected turns. The builder drops wealth-management, machine-learning and t6_report_gate trajectories with a nudge.
  • Malformed calls: The data builder also masks turns with malformed calls, such as unknown tool names, because a loss there teaches wrong names.
  • Sample boundaries: Each batch tells the model where every sample in a shared sequence begins and ends, because Qwen3.5's linear-attention layers, an attention variant that carries state along the sequence, would otherwise leak one sample into the next. This cut the largest per-token loss difference from 6.3 to 0.13, which is numerical noise.

Programs score every model; the Data section lists the task sets.

Scores and comparisons

  • Success rate: The score counts the share of tasks in the set \(T\) that pass, where \(s_t = 1\) when task \(t\) passes, so only a fully finished task earns credit. \[S = \frac{100}{|T|}\sum_{t \in T} s_t\]
  • Paired bootstrap: The comparison subtracts two models' results on the same tasks, where \(a_i\) and \(b_i\) are 100 for a correct task and 0 otherwise, and takes the 95% interval from 10,000 resamples of the \(n\) tasks. Pairing removes task difficulty from the difference, which narrows the interval; it covers task sampling only, since each test task runs once. \[\Delta = \frac{1}{n}\sum_{i=1}^{n}(b_i - a_i)\]

Finance QA and general abilities

  • Finance score: The scorer takes the first number after the last "Answer:" and marks the question correct when it is within 1% of the reference, in percent or decimal form. Every model gets the same prompt with 3 worked examples and no chat template, because a base model is not trained on chat format and scores must stay comparable. Here \(D\) is the question set, \(y_i\) the reference, \(\hat{y}_i\) the answer and \(\tau_i = 0.01|y_i|\), or 0.005 when \(y_i = 0\). \[A_{\text{fin}} = \frac{100}{|D|}\sum_{i \in D}\mathbf{1}\Big[\min_{k \in \{1,\,100,\,0.01\}}|k\hat{y}_i - y_i| \le \tau_i\Big]\]
  • MMLU: The scorer marks a knowledge question correct when the most likely option \(o\) for prompt \(x_q\) is the right option \(o^{*}_q\), over the question set \(Q\). Comparing option probabilities needs no generated format, so the base and SFT models stay comparable, and four economics and accounting subjects are left out, because financial training would raise them and hide declines elsewhere. \[A_{\text{MMLU}} = \frac{100}{|Q|}\sum_{q \in Q}\mathbf{1}\Big[\arg\max_{o}\log p(o \mid x_q) = o^{*}_q\Big]\]
  • GSM8K: The scorer marks a math word problem correct when \(\hat{a}_q\), the last number in the reply, equals the reference \(a_q\), which shows whether multi-step arithmetic survives outside the filing format. Every model gets the same prompt with 5 worked examples and no chat template, as the finance score does. \[A_{\text{GSM}} = \frac{100}{|Q|}\sum_{q \in Q}\mathbf{1}[\hat{a}_q = a_q]\]
  • IFEval: The scorer counts a prompt in the set \(P\) only when the reply meets all its program-checkable instructions \(I_p\), such as a word limit or JSON output, where \(f_{p,j}=1\) when instruction \(j\) holds, which measures following stated rules and formats as an agent must. Every model answers through a chat template that lets it reason first, and the scorer reads the text after that reasoning. The base model uses Qwen3.5's native template and a stop rule, and it scores 37.7 without a template. \[A_{\text{IF}} = \frac{100}{|P|}\sum_{p \in P}\prod_{j \in I_p} f_{p,j}\]

Agent tasks

  • Market-data test and FinSearchComp: The grader applies key-based grading from the Offline dataset tab and uses the tolerance each FinSearchComp task states.
  • DocFinQA: The grader takes the answer's last number and passes it within 1% of the reference, in percent or decimal form, or checks the same word on a yes/no question, which gives a score comparable with outside results.
  • State comparison (wealth management): The grader compares the final holdings, cash and trade records with the reference state and the answer's key numbers with their tolerances (amounts ±$0.01, rates ±0.1 percentage points). On a task the rules forbid, it checks that the banned trade did not run and the answer names the rule, because a task counts only when both the trades and the answer are right.
  • AUC and \(R^2\) bar (machine learning): AUC measures ranking quality (0.5 is random and 1 is perfect); \(R^2\) measures the share of the target's variance a model explains. The grader requires a submitted model that scores at most 0.015 AUC or 0.03 \(R^2\) below the model that generated the data on a hidden table. This bar demands correct data handling: on the development set a fixed pipeline passes 20 of 20 tasks with a log transform of skewed columns and 1 without it.
  • pass@1 and pass@4: The scorer computes both scores over \(T_4\), the development tasks with 4 valid attempts, where \(c_t\) of the \(n_t\) valid attempts at task \(t\) pass. \[P_1 = \frac{100}{|T_4|}\sum_{t \in T_4}\frac{c_t}{n_t}\] \[P_4 = \frac{100}{|T_4|}\sum_{t \in T_4}\mathbf{1}[c_t \ge 1]\]

Task selection is running; training has not started, and every training value here is planned. DAPO is the next reinforcement learning (RL) method. It builds on GRPO, which samples a group of attempts at each task and scores each attempt against its group. DAPO adds the first four changes below and removes the KL penalty, an extra loss that holds the model close to a frozen copy of itself. Training will use verl's own DAPO implementation and start from the SFT model above.

  • Clip-Higher: Training limits how far one update may move a token's probability: the ratio of its new to its old probability may fall by at most 0.2 and rise by at most 0.28.
  • Dynamic Sampling: verl's trainer drops a group whose 8 attempts all earn the same grade, all passed or all failed, whatever their lengths, and dispatches 2 refill tasks for it, because such a group holds no pass-or-fail difference and would train only on length. The refill has no cap, so a step takes longer as more groups are dropped.
  • Token-level loss: token-mean averages the loss over all tokens directly, so the tokens of a long attempt keep their full weight.
  • Overlong reward shaping: verl's DAPO reward manager adds a length reward to the grade \(r\): 0 up to \(L_s\), then falling linearly to −1 at the budget \(L_{\max}\). An attempt that fills the budget always fails, so it totals −2, and it carries loss. Here \(L\) counts an attempt's tokens with tool results, the buffer is \(L_c = 4{,}096\) and \(L_s = L_{\max} - L_c = 24{,}576\); the budget \(L_{\max} = 28{,}672\) plus a 4,096-token prompt equals the 32,768-token SFT sequences. \[R = r + \min\Big(-\frac{L - L_s}{L_c},\ 0\Big)\]
  • Reward: The grader gives +1 for a pass and −1 otherwise, as DAPO does. With 0/1 grades the same length penalty would weigh twice as much against the gap between right and wrong.
  • No KL: Training applies no KL penalty, because with long reasoning the model is expected to move far from where it started; this also saves that copy's memory and forward pass.
  • Task selection: The SFT model attempts each pool task 8 times, and selection drops tasks with 0/8 passes, keeps tasks with 1–7/8 and keeps 10% of tasks with 8/8, because a task with the same grade in all attempts gives the group comparison nothing. The kept 10% leaves some solved tasks for the model to keep practicing. If more remain, a draw within each task type, in proportion to the type's share, holds the set to an average of 93.9 tasks per type, which largely sets how many times a run passes over its tasks. The model changes during training, so a selected task can also come to be all passed or all failed, and dynamic sampling keeps dropping such groups at each step.
  • Task pool: The market part of the pool holds newly generated tasks, 200 in each of 10 task types, and none of them repeats an SFT training, development or test task. 200 DocFinQA training tasks join as an eleventh type if a short trial run on 2 such tasks passes, because without them RL has no signal to keep the SFT model's reading ability.
  • Settings: On 8 GPUs, each step takes 128 tasks with 8 attempts each, in mini-batches of 32 tasks, which gives 4 updates per step; the run lasts 21 steps at a learning rate of 1e-6, and an attempt stops at 30 task turns.

not started The final DAPO model will run the market-data, FinSearchComp, DocFinQA, development, wealth-management, machine-learning and general-ability sets under the SFT evaluation tab's rules, for comparison with the base, teacher and SFT models, with three additions.

  • Strict grading: The strict grader adds four rules to market-data, FinSearchComp and development answers, and \(r_t = 1\) when all hold. An answer may hold at most 50 numbers outside dates. It may hold at most 40 distinct dates. Each number key must appear outside any date. On a task with candidates, the first company named must be correct and each later company key must be followed by its value. The original grader accepts a key anywhere in the answer: an audit's answers that knew no reference value, only the restated task and grids of numbers, passed 209 of 939 RL training tasks, so an RL gain under the original grader alone could not be trusted. \[S_{\text{strict}} = \frac{100}{|T|}\sum_{t \in T} s_t\, r_t\]
  • Reworded test: Rewording rewrites the 300 market-data test tasks with the same parameters and answers and lowers their 5-gram overlap with same-type training tasks from 0.77–0.99 to 0.10–0.32, so a score change shows how much a result depends on wording. \[\Delta_{\text{reword}} = S_{\text{reworded}} - S_{\text{original}}\]
  • Paired gain over the SFT model: The comparison takes \(a_i\) from the SFT model and \(b_i\) from the final DAPO model on each task under the paired bootstrap of the SFT evaluation tab.

Quantitative Results

Agent SFT lifts the 4B model from 16.7% to 87.3% on held-out market-data tasks
