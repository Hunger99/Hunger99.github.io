Abstract

This project plans nine post-training settings for Qwen3.5-4B-Base across five datasets: the existing financial question-answering and instruction-following tasks, FinDeepResearch company reports, and a Kaggle-derived MLE-bench project subset. Multi-turn supervised fine-tuning (SFT) teaches verified demonstrations; DAPO then learns from tool-assisted attempts and task-specific rewards. We plan to generate additional synthetic tasks for FinSearchComp, FinDeepResearch and the MLE-bench project subset; DocFinQA and IFEval retain original tasks only. Every setting will share frozen original cohorts and an evaluation protocol, separating the effect of adding synthetic tasks at SFT, DAPO or both stages. The new task adapters still need evidence, grading and execution qualification; the new training experiment has not started.

Method Pipeline

Canonical reports → Task contracts → Source isolation → Frozen pools

One original report version represents each filing

  • Canonicalization: The entry filter groups DocFinQA reports by registrant and fiscal end, selects one verbatim version by source quality and preserves the alternatives and source hashes. This keeps equivalent reports from appearing as different source documents.
  • Evidence retention: Post-selection checks quarantine questions that lose required source operands; they do not rewrite reports or choose versions by model scores.
  • Original filing semantics: Before financial generation, source checks bind the metric meaning, consolidated report context, period, unit and sign to the original filing. Negative debt deductions are rejected or quarantined rather than converted to a positive balance; source approval does not itself qualify a task.

A common outer interface preserves each task’s native output

  • Task adapter: The planned five-dataset interface will bind source identities and input artifacts, an isolated tool trajectory, a submitted artifact and a dataset-specific grader result. Sharing this outer record lets one runner manage different tasks without converting report writing or ML engineering into question answering.
  • Qualification: New adapters must pass evidence-access, native-grader, artifact-validation and evaluator-isolation checks before admission. The Data Sets table defines the task outputs and metrics; the pool table distinguishes frozen cohorts from runnable tasks.

Source identities precede question sampling

  • Decontamination: The splitter checks report identities, normalized questions, task ancestry and financial support periods across roles. Unresolved report identities remain outside the eligible pools.
  • Stratification: DocFinQA retains its official split membership and a proportional half of each numeric/boolean stratum; FinSearchComp and IFEval use deterministic category-aware project splits. This preserves category coverage while retaining test questions.

One release serves every model setting

  • Immutable inputs: Existing original task IDs, text, canonical sources and graders are bound to a frozen release. New cohorts and adapters will join the same shared release only after qualification; the candidate tables hold their counts and state.
  • Reserved evaluation: Synthetic validation and test items use separate source support and independent review. Their acceptance quotas do not authorize filling a shortfall with duplicates or unreviewed candidates.

Programs expand reproducible weaknesses

  • Financial diagnostics: The generator separates errors in amount, company, period and unit from formatting or source-identity failures before choosing a capability to strengthen. This prevents format failures from being mistaken for difficult financial reasoning.
  • Programmatic generation: Source-bound templates vary facts and dependencies for repeatable weak skills. The strengthened financial compiler filters the complete candidate set, selects a unique eligible company and derives the comparison company only after selection; fixed names cannot disclose the answer.

Claude proposes supported tasks from fixed sources

  • Source-bound generation: Opus 5.5 at Extra High effort selects a structured plan from a reviewed source bank. The host compiler renders the learner task and computes its reference; author-written prose and private answers do not become authoritative task content.
  • Coverage: Typed financial generation covers supported SEC retrieval and dependent calculations. Separate report and ML candidate adapters retain report rubrics or native competition artifacts. Unsupported proposals are quarantined; these contracts do not establish broad discovery of every uncovered capability.

Both branches produce new, source-bound candidate identities

  • Canonical task: The latest strengthened financial contract normalizes node and output labels and renders selection, ranking, comparison and unit rules from typed fields. A substantive change produces a new task identity and invalidates earlier reviews.
  • Candidate inventory: One immutable semantic inventory groups equivalent supported tasks across both branches and fixes their SFT, DAPO, validation or test role. Duplicate aliases retain their history but cannot add a quota slot or repeat a paid review through the guarded path.

Accounting runs before and after each native request

  • Request sequence: The host binds the complete prompt and reserves the maximum in-flight cost under a shared lock before sending a fresh native Messages conversation through CLIProxyAPI. Authors use a conservative configured input bound; blind-solving and critic roles use calibrated native input-token counts. The host then saves the raw response and settles actual token usage in the append-only ledger. Generation uses Extra High; blind solving and criticism use Medium.
  • Failure handling: Failed and retried calls consume the same authorization; missing usage, changed input or an exceeded bound stops subsequent calls. The proxy forwards explicit caller prompts; OAuth metadata and billing fields remain, so this is not claimed to be a zero-overhead direct API.
  • Execution scope: Independent candidates may run concurrently only after source, inventory and spending checks pass. The strengthened current financial contract still needs fresh live review; prior-version acceptance does not transfer. Formal training qualification is separate from candidate generation.

Source meaning and independent answers must agree

  • Financial reference: Independent arithmetic implementations check the answer, units, source periods and rounding. Candidate selection must be complete, effective and unique; ties, unsupported facts, missing dependencies and zero denominators are rejected.
  • Semantic deduplication: The guarded typed-review entry accepts only the canonical inventory member before a paid review. The key preserves supported economic meaning and source periods while ignoring branch or cosmetic labels; it does not prove equivalence of arbitrary prose or algebra.

The host executes the actual source reads and submissions

  • Sandbox replay: Financial solvers must query the fixed read-only snapshot and match an independently calculated answer. ML checks validate the exact source, feature family, row identity and native grader; hidden labels remain evaluator-only, and native identifiers are restored by the host only after submission closes.
  • Retrieval evidence: Host records bind real queries, returned data, code and snapshot identity. A real model → retrieval → model check confirmed that returned evidence entered the follow-up model request; intervention tests separately check evidence use by retained model-written code. This does not prove every internal reasoning step or replace a full same-model tools-on/tools-off comparison.
  • Report validation: A report needs complete sections, supported citations, correct calculations and its declared rubric. A heading or citation-structure check alone cannot certify financial content; independent expert targets and future data stay outside the learner corpus.

Independent model roles must survive executable counter-checks

  • Blind solve: A fresh Medium conversation receives the learner task and tool contract without the private answer. The host executes the returned solver and grades the actual result.
  • Adversarial review: A separate Medium conversation checks ambiguity, missing evidence, units, answer leakage and grader loopholes. Its distinct counter-solver must also execute correctly; a plausible review sentence is insufficient.
  • Evidence adjudication: A memory-based objection can be reconsidered only with independent source proof bound to that exact task, response and execution. Original reject or unresolved judgments remain preserved; unresolved substantive concerns keep the task quarantined.

Passing a sample does not release a training dataset

  • Version-bound checks: The prior-contract programmatic FSC, Claude FSC and ML acceptance samples completed real blind and adversarial checks. The latest strengthened financial contract needs its own fresh reviews; no earlier verdict is silently reassigned.
  • Production boundary: The semantic-inventory guard currently covers the new typed review path. Legacy continuous, batch, graph and cycle paths require the same guard or routing through it before formal use. Question quality, difficulty, complete demonstration and final dataset release remain separate decisions.
Recorded attempts → Difficulty measurement → Demonstration admission

The harness saves model actions and real tool results

  • Recorded execution: Financial tasks use read-only evidence tools and restricted Python; report and ML adapters add their declared source documents or data artifacts. Model messages, tool calls, results and completion state are preserved. The Harness section describes context, tools and correction behavior.
  • IFEval: Its final answer is scored with the fixed strict instruction checker. Financial evidence requirements are not applied to instruction-only answers.

Local teacher and student trials determine the training route

  • Difficulty measurement: Multiple teacher and student attempts use training or calibration tasks only. A larger teacher supplies candidate demonstrations, while student successes and failures distinguish unstable skills from tasks requiring diagnosis or SFT support.
  • DAPO signal: A group needs reward variation to distinguish better attempts. Always-correct or always-wrong groups do not automatically provide a useful DAPO learning signal, and sealed test outcomes never choose training difficulty.

Complete, grounded demonstrations qualify separately

  • Trace qualification: Admission checks source receipts, successful evidence reads, tool schemas, grounding, units and task completion, followed by independent trajectory review. A historical trace cannot be rebound to a different source or revised question without matching proof.
  • Report collection: The implemented collector can divide one unchanged report task into independent report-section and sentiment contexts, with bounded concurrency and append-only raw artifacts. These contexts and fragments remain one parent task and are not represented as one continuous model trajectory.
  • Current report result: The latest bounded local pilot retained 25 of 110 required labels and 10 report fragments; it produced no complete parent report or qualified training demonstration. Partial output is preserved and cannot fill the synthetic quota.
  • Training release: Qualified questions, qualified demonstrations and tokenizer-bound packed data are separate products. Only complete reviewed trajectories proceed to exact token, mask and common-release checks.

Two supervised checkpoints serve the comparison

  • Supervised fine-tuning: S0 will train on admitted demonstrations from the common original pool; S1 will add admitted demonstrations for the fixed shared pool of synthetic SFT tasks. Both will independently start from the same Base and follow the same two phases, with identical original tasks and evidence views; the pool table defines eligible synthetic tasks and their qualification state.

Phase 1 supplies the evidence needed for reasoning

  • Given-evidence reasoning: The first phase will supply all facts needed for the task and permits Python calculation, so the model can learn financial reasoning, unit conversion, conditional calculations, self-checking and instruction following.
  • Phase assignment: Verified missing information determines the phase, rather than the dataset name or Python use. Unverified evidence views remain held.

Phase 2 retrieves missing evidence before reasoning

  • Retrieval and reasoning: The second phase will use tasks that require information absent from the prompt, so the model must retrieve authorized sources and align entities, periods and units before reasoning.
  • State continuity: One training run will retain the optimizer, which holds the parameter-update state, and the learning-rate schedule across both phases, saving their full state with the model. Each model’s second phase will continue its own first-phase state.

Only verified assistant behavior contributes to loss

  • Loss masking: Admitted assistant reasoning, tool calls and final answers receive supervision; system and user text, tool returns and invalid assistant content provide context only. Complete trajectories retain their masks and tokenizer binding; overlong or infeasible schedules are held without clipping.
  • Shared budget: Each condition has one total of 6,553,600 supervised tokens and 100 updates, initially split into 3,276,800 tokens and 50 updates per phase. These tokens count supervised exposure; existing loss averaging is unchanged, and the initial allocation has not been evaluated.
  • Launch gates: The new SFT stage has not started. Evidence, method review, actual paired probes where required, complete demonstrations, fixed synthetic pools and exact budget checks must pass before the common five-dataset training gate can open.

Six reinforcement-learning jobs complete the nine settings

  • Matched continuations: Each SFT checkpoint and the original Base model receives an original-only DAPO continuation or one that also uses synthetic tasks. Candidates and Settings identifies the shared task pools.
  • Dynamic filtering: DAPO filters groups without reward variation. Record tasks retained after filtering, updates, generated tokens and tool-compute exposure; planned report and ML grading-to-reward adapters must be qualified before those tasks enter training.

The soft penalty counts model-generated tokens

  • Generated-token penalty: The repository reward manager excludes tool returns, inserted context and padding from the soft length penalty. The hard response budget still includes the full context, keeping the resource limit explicit.

Unfinished attempts contribute no policy loss

  • Whole-rollout masking: An unfinished truncated or aborted rollout has its entire policy mask zeroed. Completed wrong answers remain trainable, and an entirely masked microbatch returns finite loss and gradients.
  • Launch gates: These fixes are implemented and CPU-checked; the new six-job experiment has not started. Shared data, checkpoints and executable budget controls must be ready before launch.

Every stage is measured on the same original tasks

  • Shared protocol: Base, SFT and DAPO outputs use the same task IDs, tool conditions, sampling policy and grader versions. This makes stage-to-stage comparisons possible.

  • Separate reporting: Report each qualified synthetic challenge separately from its original cohort. A project-derived report or ML challenge retains its own task requirements and grader; its result does not replace the official source benchmark score.
  • Limits: A larger synthetic test measures coverage of generated task families. Generalization claims remain limited to the held-out sources, task families and execution budgets actually evaluated.

Harness

The Harness is the runtime around the model: it manages the conversation, executes declared tools and returns observations and correction feedback. The same environment interface selects tools and grading rules for each task type. H1 is the configuration of this runtime that adds a checklist, constraint checks, verification and bounded correction; these extra controls apply when an attempt selects H1.

Context preserves what the model actually saw

Each episode starts with its environment prompt and task. Messages are appended without rewriting previous turns; Qwen retains its previous reasoning when the serving template supports it. New tool results are capped when produced (8,000 characters by default), with an explicit truncation notice; searches, document reads and long lists use pages or bounded ranges. Run settings bound task turns, checklist updates, correction turns and each model reply; context overflow ends the attempt.

Feedback supports correction; admission checks the saved result

The host parses tool arguments as JSON and dispatches only known tools. H1 checks declared writes before execution; known-tool execution errors include a valid-call example when H1 correction is enabled, and repeated identical calls receive a hint. On finish, H1 checks checklist completion and the environment's evidence or output requirements, then returns specific failures for a bounded number of corrections. Exhausting that allowance can end the episode, so completion alone does not establish correctness.

Independent graders evaluate the saved answer or submission. Financial number matching is a grounding check, not a proof of reasoning; actual source-query records and replay checks provide additional evidence. Question approval, complete demonstration approval and training admission remain separate gates.

Synthetic-data roles use a separate Messages route

Authors, blind solvers and adversarial reviewers receive separate fresh API requests with explicit caller prompts. Before the native-proxy request, the client checks the frozen task/source scope and spending reservation. Authors reserve against a conservative configured input bound; blind solvers and critics use calibrated native input-token counts. After the request returns, usage and failed attempts enter the append-only ledger. Blind solvers write code for the host to execute: the API text request itself does not execute tools. A critic receives actual replay evidence without inheriting an earlier review verdict.

These runtime controls are implemented in the episode loop, v2 environment adapter and bounded native-API acceptance runner. The FinDeepResearch collector and MLE runtime remain candidate/pilot paths; their execution does not grant training admission.
