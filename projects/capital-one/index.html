Abstract

This project plans nine post-training settings for Qwen3.5-4B-Base across five datasets: the existing financial question-answering and instruction-following tasks, FinDeepResearch company reports, and a Kaggle-derived MLE-bench project subset. Multi-turn supervised fine-tuning (SFT) teaches verified demonstrations; DAPO then learns from tool-assisted attempts and task-specific rewards. Augmentation is planned for FinSearchComp and the two new datasets; DocFinQA and IFEval retain original tasks only. Every setting will share frozen original cohorts and an evaluation protocol, separating the effect of adding synthetic tasks at SFT, DAPO or both stages. The new task adapters still need evidence, grading and execution qualification; the new training experiment has not started.

Method Pipeline

Select a stage to see what it does.

→ → → → → →
Canonical reports → Task contracts → Source isolation → Frozen pools

One original report version represents each filing

  • Canonicalization: The entry filter groups DocFinQA reports by registrant and fiscal end, selects one verbatim version by source quality and preserves the alternatives and source hashes. This keeps equivalent reports from appearing as different source documents.
  • Evidence retention: Post-selection checks quarantine questions that lose required source operands; they do not rewrite reports or choose versions by model scores.

A common outer interface preserves each task’s native output

  • Task adapter: The planned five-dataset interface will bind source identities and input artifacts, an isolated tool trajectory, a submitted artifact and a dataset-specific grader result. Sharing this outer record lets one runner manage different tasks without converting report writing or ML engineering into question answering.
  • Qualification: New adapters must pass evidence-access, native-grader, artifact-validation and evaluator-isolation checks before admission. The Data Sets table defines the task outputs and metrics; the pool table distinguishes frozen cohorts from runnable tasks.

Source identities precede question sampling

  • Decontamination: The splitter checks report identities, normalized questions, task ancestry and financial support periods across roles. Unresolved report identities remain outside the eligible pools.
  • Stratification: DocFinQA retains its official split membership and a proportional half of each numeric/boolean stratum; FinSearchComp and IFEval use deterministic category-aware project splits. This preserves category coverage while retaining test questions.

One release serves every model setting

  • Immutable inputs: Existing original task IDs, text, canonical sources and graders are bound to a frozen release. New cohorts and adapters will join the same shared release only after qualification; the candidate tables hold their counts and state.
  • Reserved evaluation: Synthetic validation and test items use separate source support and independent review. Their acceptance quotas do not authorize filling a shortfall with duplicates or unreviewed candidates.
Program branch Claude branch Native requests

Programs expand reproducible weaknesses

  • Financial diagnostics: The diagnostic separates financial errors in amount, company, period or unit from formatting and source-identity failures before choosing tasks to strengthen. Historical scores and admission decisions stay unchanged.
  • Programmatic generation: The generator varies a declared task contract over trusted financial facts and explicit periods, units and calculations. This supplies repeatable practice for unstable or consistently missed capabilities without copying reserved questions.
  • Structural strengthening: The compiler can filter a complete set of candidates, select a unique eligible company, then compute a dependent comparison. A changed task requires regenerated reference answers and fresh independent review.

Claude selects questions within a verified contract

  • Source-bound generation: Claude selects supported structures and parameters from trusted source cases and training capabilities. A compiler controls the learner question and reference computation so generated prose cannot silently introduce facts or an authoritative answer.
  • Scope: The current program and typed Claude routes cover four fixed SEC retrieval/calculation families and reject unsupported structures; discovery of uncovered capability families remains unimplemented.

Fresh Messages requests separate the roles

  • Native proxy: The client uses the native Messages interface of CLIProxyAPI with explicit caller prompts and a fresh conversation for each role. Generation requests use Opus 5.5 Extra High effort; blind solving, adversarial review and trajectory review use Medium.
  • Accounting: A shared append-only ledger enforces total, call-count and role-specific limits. Failed requests remain recorded; missing accounting blocks further calls.
Independent answers → Tool execution → Blind and adversarial review

Independent computation checks the answer contract

  • Reference agreement: Separate arithmetic implementations must agree on the answer, units and required source periods. Equivalent instances are deduplicated before any quota is counted.

Real tools check source availability

  • Sandbox replay: For current financial QA, reference code queries the fixed read-only snapshot through the learner’s restricted tool runtime and must match the independent answer. Planned report and ML tasks must instead pass their native artifact and grader checks; metadata claims alone cannot qualify execution.
  • Paired probes: The implemented runner can compare the same question with source retrieval enabled and with calculation-only tools that cannot read the source snapshot. Actual records from both model attempts and a review of the task’s required information are still needed; missing records keep evidence views and demonstrations pending.

Blind solving and adversarial review remain independent

  • Blind solve: A fresh Claude conversation receives the learner question and tool contract without the private answer. Its solver is executed and independently graded.
  • Adversarial review: A separate conversation checks the question, reference, solver and actual execution for ambiguity, periods, units and grading loopholes without receiving an earlier verdict. Both reviews must pass before question admission.
Agent harness → Difficulty measurement → Demonstration admission

The harness records the evidence used by the model

  • Tool interface: Current financial QA uses read-only market, SEC and FRED queries, report retrieval and restricted Python. Messages, tool calls and results are saved as trajectories; explicit submission ends an attempt. Planned report and ML adapters will attach source evidence or competition artifacts and keep expert targets and hidden labels outside the learner’s tools.
  • IFEval: Its final answer is scored by the strict instruction checker with fixed scoring randomness. Financial evidence requirements are not applied to instruction-only answers.

Local models measure solvability before training

  • DAPO comparison: Multiple attempts at the same task form a group. DAPO compares their scores to favor better attempts; when the task scores are all equal, the group cannot distinguish better attempts and is filtered.
  • Teacher and student: A larger local teacher supplies candidate demonstrations, while student trials measure success patterns. Always-unsolved tasks need diagnosis or SFT support; they do not automatically supply a DAPO learning signal.
  • Reserved tasks: Calibration uses only training or calibration material. The sealed test is excluded from difficulty selection.

A correct final answer alone is insufficient

  • Trace qualification: Admission checks successful evidence reads, tool schemas, grounding, units, completion and source receipts. A historical trajectory cannot be rebound to a newly selected report without matching source evidence.
  • Separate products: Approved questions, approved demonstrations and packed training data are different outputs. Missing demonstrations or unreviewed candidates keep training entry closed.

Two supervised checkpoints serve the comparison

  • Supervised fine-tuning: S0 will train on admitted demonstrations from the common original pool; S1 will add the fixed shared SFT augmentation pool. Both will independently start from the same Base and follow the same two phases, with identical original tasks and evidence views; the pool table defines eligible augmentation and its qualification state.

Phase 1 supplies the evidence needed for reasoning

  • Given-evidence reasoning: The first phase will supply all facts needed for the task and permits Python calculation, so the model can learn financial reasoning, unit conversion, conditional calculations, self-checking and instruction following.
  • Phase assignment: Verified missing information determines the phase, rather than the dataset name or Python use. Unverified evidence views remain held.

Phase 2 retrieves missing evidence before reasoning

  • Retrieval and reasoning: The second phase will use tasks that require information absent from the prompt, so the model must retrieve authorized sources and align entities, periods and units before reasoning.
  • State continuity: One training run will retain the optimizer, which holds the parameter-update state, and the learning-rate schedule across both phases, saving their full state with the model. Each model’s second phase will continue its own first-phase state.

Only verified assistant behavior contributes to loss

  • Loss masking: Admitted assistant reasoning, tool calls and final answers receive supervision; system and user text, tool returns and invalid assistant content provide context only. Complete trajectories retain their masks and tokenizer binding; overlong or infeasible schedules are held without clipping.
  • Shared budget: Each condition has one total of 6,553,600 supervised tokens and 100 updates, initially split into 3,276,800 tokens and 50 updates per phase. These tokens count supervised exposure; existing loss averaging is unchanged, and the initial allocation has not been evaluated.
  • Launch gates: The new SFT stage has not started. Evidence, method review, actual paired probes where required, complete demonstrations, fixed synthetic pools and exact budget checks must pass before the common five-dataset training gate can open.

Six reinforcement-learning jobs complete the nine settings

  • Matched continuations: Each SFT checkpoint and the original Base model receives an original-only or augmented DAPO continuation. The Baselines table identifies the shared task pools.
  • Dynamic filtering: DAPO filters groups without reward variation. Record tasks retained after filtering, updates, generated tokens and tool-compute exposure; planned report and ML grading-to-reward adapters must be qualified before those tasks enter training.

The soft penalty counts model-generated tokens

  • Generated-token penalty: The repository reward manager excludes tool returns, inserted context and padding from the soft length penalty. The hard response budget still includes the full context, keeping the resource limit explicit.

Unfinished attempts contribute no policy loss

  • Whole-rollout masking: An unfinished truncated or aborted rollout has its entire policy mask zeroed. Completed wrong answers remain trainable, and an entirely masked microbatch returns finite loss and gradients.
  • Launch gates: These fixes are implemented and CPU-checked; the new six-job experiment has not started. Shared data, checkpoints and executable budget controls must be ready before launch.

Every stage is measured on the same original tasks

  • Native metrics: Evaluate each dataset with the definitions and formulas in the Data Sets table. Report QA accuracy, strict instruction following, report quality and ML competition performance separately, with each native metric’s direction and evaluation cohort.
  • Shared protocol: Base, SFT and DAPO outputs use the same task IDs, tool conditions, sampling policy and grader versions. This makes stage-to-stage comparisons possible.

The added test probes independently reviewed synthetic tasks

  • Separate reporting: Report each qualified synthetic challenge separately from its original cohort. A project-derived report or ML challenge retains its own task requirements and grader; its result does not replace the official source benchmark score.
  • Limits: A larger synthetic test measures coverage of generated task families. Generalization claims remain limited to the held-out sources, task families and execution budgets actually evaluated.

Paired differences isolate the declared intervention

  • Stage comparisons: Compare S1 with S0 for the SFT increment; compare augmented and original DAPO from the same checkpoint for the DAPO increment; compare each DAPO result with its own starting checkpoint for the extra-training effect.
  • Selection: Only validation guides checkpoint and mixture selection. Final paired confidence intervals use the common frozen test and do not feed the data generator.
