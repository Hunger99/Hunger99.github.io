Post-Training a 4B Financial LLM Agent
with Multi-Turn Agent SFT and DAPO

Sponsored Practicum Project
Sep. 2026 – mid-Nov. 2026 (expected)
Ongoing Project
Code

On tasks of the trained types, multi-turn agent SFT takes the 4B model from 16.7% to 88.7%, past the official Qwen3.5-4B (57.7%). On FinSearchComp tasks written outside the project it reaches 77.6%, past the official model's 64.3%.

Abstract

This project post-trains a 4B base model, Qwen3.5-4B-Base, into a tool-using financial agent that looks up market prices, macroeconomic series and company filings, computes over them in a Python sandbox and answers multi-step questions. The official post-trained Qwen3.5-4B already solves 84.7% of our earlier market-retrieval development tasks, so we built a harder offline dataset of 3,148 tasks (2,350 training, 200 development and 598 test tasks). Of these, 2,850 are generated in the style of the public benchmark FinSearchComp over a fixed data snapshot, with answers computed by programs and rechecked by an independent implementation. A teacher, the larger model Qwen3.8-27B, solves the market training tasks of two difficulty tiers inside an agent harness, the code that gives a model its tools and checks its answers, and each attempt is saved as a trajectory, the full record of its messages, tool calls and tool results. These trajectories, after filtering, with filtered wealth-management and machine-learning trajectories and 2,000 samples from a 1:1 mix of finance and general data, train the 4B model with multi-turn agent SFT (supervised fine-tuning, which continues training on examples with known answers). On 300 market-data test tasks from held-out stocks and later periods, the SFT model solves 88.7%, against 57.7% for the official Qwen3.5-4B, 16.7% for the base model and 94.7% for the teacher. The next step, reinforcement learning with DAPO from a retrained SFT model, has not started.

Pipeline

Selection → Synthesis → Filtering → Deduplication → Mixing

The stages run in this order. Before them, a converter rewrites every source into one sample format with the fields id, source, messages and meta, so decontamination, deduplication and sampling can run the same program on every source. The single-turn mixes built here served the project's early experiments: the reported SFT model comes from one multi-turn agent SFT run from Qwen3.5-4B-Base, which takes only a 2,000-sample slice of the 1:1 mix.

Selection decides which sources and documents enter

  • Source selection: The finance pool leaves out Sujet-Finance-Instruct-177k and Finance-Instruct-500k, because at their available size they would take 69% of the finance part and leave 3.1% to FinQA, TAT-QA, BizBench and DianJin, the sources of the finance score's own task type, so training would barely practise that task.
  • Language filter: The converter keeps only the English samples of IndustryInstruction and Agentar, meaning samples with no Han character and at least 90% ASCII among their letters. The project trains an English financial model on English tasks, so a non-English sample would spend training on a language no task uses.
  • Length cap: The converter counts a sample's tokens over its messages and reasoning and drops any sample over 4,096 tokens instead of cutting it, since a cut would keep the reasoning and lose the answer. A token is the unit a model splits text into, about 1–2 per English word.
  • Seed split: A salted hash, which hashes an id together with a fixed string so the result is reproducible, sends FinQA training questions by report page and TAT-QA training questions by table into 80% training samples and a 20% hold-out, because a page often carries several questions and a split by question would let the hold-out share excerpts with training.
  • Quality tier + rule filter: The document filter takes the English high-quality tier of IndustryCorpus2's finance articles and keeps documents with a num_words field of 200–100,000, at most 30% repeated non-empty lines and no Han character. The word range drops fragments and oversized dumps and the repeated-line limit drops boilerplate, so question writing starts from real English finance text.
  • Chunk selection: The chunker joins consecutive lines of a kept document into chunks of 1,000–2,000 characters, takes at most 2 chunks per document and passes on only chunks with at least 4 numbers. A chunk of this size holds enough context for one self-contained question, at least 4 numbers give a calculation its inputs, and the 2-chunk limit spreads the questions across documents. It uses finance articles instead of 10-K filings because finance-score tasks come from listed companies' annual reports, and generating from 10-Ks could put a training question in a report that a test task uses.

Synthesis generates tasks, trajectories and questions

  • Task synthesis: Programs, not an LLM, generate market, wealth-management and machine-learning tasks: seeded templates draw a task's parameters, and the same program computes from the data what grading compares with: a reference answer, a reference state or, for a machine-learning task, the score of the model that generated the data. A computed reference gives grading and the filters a basis they can trust, and a seed makes each task reproducible.
  • Market tasks: Templates draw entities and time windows from a fixed data snapshot, as the Offline dataset tab explains.
  • Wealth-management tasks: A program builds a SQLite business database of 2,000 customers, 300 products and two years of daily net asset values, and 14 task types draw multi-step tasks on it under 7 business rules. Training, development and test each use their own database, so a test task meets customers and products the model has not seen. The rules forbid about 15% of the tasks so that grading can test whether the agent refuses a violating action.
  • Machine-learning tasks: Two templates draw a fresh data table from each task's seed, the agent builds a model through structured tools, and a program scores it on a hidden test table, where it must come close to the score of the model that generated the data, so a task tests correct data handling, not only a finished run.
  • Teacher trajectories: Qwen3.8-27B attempts the training tasks in the harness, which records every message and tool call. One attempt per task suffices on the original tier, where the teacher solves nearly every development task; two attempts per task give the hard tier about twice the trajectories; wealth-management and machine-learning tasks get 2 attempts, 4 when fewer than 2 pass and up to 8 when all 4 fail, since tasks the teacher misses at first are often the ones most worth learning.
  • Synthetic document QA: A locally hosted LLM writes 1–2 calculation questions per chunk that must use the chunk's financial figures, each with a worked calculation and one numeric answer, and it asks nothing about dates or durations. The task matches the finance score's FinQA and TAT-QA test tasks, given material and compute a number, so the ablation below measures the synthetic data itself and not a different task type.
  • Question checks: The checker keeps a question only if every number it lists occurs in the chunk, the numbers are not all years, and a second answer from the chunk and question alone agrees within 1%, since these questions have no human reference and the second answer blocks miscalculated or misread ones. A model's spot check judged 93 of 100 kept questions correct.
  • Ablation of synthetic document QA: An ablation removes one part to measure what it adds: on Qwen3-4B-Base the 1:1 mix scores 0.05 points below the same mix without synthetic samples on the finance score (95% interval −1.3 to +1.2, p=0.55). Other finance sources filled the freed places, which may offset the effect, but the data shows no measurable gain beyond the existing finance data, so the project adds no new synthetic volume.

Filtering deletes what would mislead a score or teach a bad habit

Sample filters

  • Decontamination: Decontamination deletes a training sample from any source when it repeats or closely copies a reference task, because otherwise the finance score could reward memory of a seen task. The reference tasks are the validation and test questions of FinQA, TAT-QA and XFinBench, plus public knowledge, math and instruction-following benchmarks and the 20% seed hold-out. The four checks below are the main triggers, and excerpt sources have further match rules, because copies change a table's layout, copy part of a table or reword the question, and no single check catches them all.
  • 8-gram decontamination: An 8-gram is a run of 8 consecutive tokens, and decontamination deletes a sample when its 8-grams cover at least 50% of a reference task's tokens. The check ignores 8-grams made of a single number and needs at least 2 distinct 8-grams against XFinBench and those public benchmarks, because number-heavy tasks would otherwise delete thousands of normal samples.
  • Format-stripped 8-gram: Decontamination repeats the 8-gram check after removing table separators, JSON symbols and other punctuation, because a copy that only changes the table format escapes the plain check.
  • Embedding decontamination: An embedding model turns text into a vector, and cosine similarity, the cosine of the angle between two vectors, rises as meanings get closer. Decontamination compares each user turn with the reference tasks and deletes the sample at a bge-m3 cosine similarity of at least 0.90, or at a Nemotron-3-Embed-1B cosine similarity of at least 0.72 against those public benchmarks or 0.845 against other reference tasks, because reworded copies escape 8-grams and each embedding model misses some. The lower cut-off against those benchmarks catches more of their reworded copies, and the higher one against finance references spares samples that only come from another page or year of the same company, which the project keeps.
  • Number-overlap matching: On the five sources with report excerpts (FinQA, TAT-QA, DianJin, BizBench, Agentar), decontamination compares a sample with the distinctive numbers of a reference excerpt, which leave out whole numbers under 100 and years. If the excerpt has 8 or more such numbers, a sample holding at least half of them is deleted; if it has 4–7, a sample holding at least 75% of them and at least 4 is deleted. A table rewritten in another layout keeps its numbers, so this catches copies that 8-grams miss.
  • Grounding filter: The grounding filter deletes an IndustryInstruction sample when its prompt, under 600 characters, cites an article or data it leaves out, or when its answer has 2 or more specific numbers (above 12 and not a year) missing from the prompt, because such samples teach the model to write numbers that are not in its material.

Trajectory filters (8), each reading what the previous one left

  • Correct answer: The filter keeps a trajectory only if it passes grading, so the model does not learn a wrong method.
  • Normal ending: The filter deletes a trajectory that ended on the step limit, the context limit, or a service or harness error, because such a run stops without a normal finish for the model to imitate.
  • No cut output: The filter deletes a market trajectory with a reply that reached the per-call output limit of 4,096 tokens, because imitating a reply that stops mid-text or mid-call teaches unfinished output; only market trajectories record this.
  • Supported answer: The filter deletes a trajectory with 2 or more rejected finishes, because after the second rejection the harness accepts a finish unverified, so its answer has no verified support.
  • No loop: The filter deletes a trajectory that repeats a call with the same arguments 3 or more times or drew a loop hint, because repeated identical calls add no information and would teach wasted steps.
  • Tool errors: The filter deletes a trajectory with more than 2 tool errors, because a path full of failed calls would teach the model to write calls that fail.
  • Step count: The filter deletes a trajectory with more than twice the median step count of its source and task type, because a fixed percentile cuts a tenth of every task type and hits the harder instances first: on 1,525 teacher trajectories the 90th percentile removes 76 and twice the median removes 1.
  • Method judge: The teacher reads a market task, its reference solution, the trajectory's calls and results and the final answer, and the filter deletes a trajectory it judges flawed or cannot parse. This runs only on market tasks because key-value grading can pass a wrong method by luck, such as a small count or a window with no split, while wealth-management grading checks the final state. The judge was validated on only 40 trajectories.

Task filters (3)

  • Entity-and-window decontamination: The filter deletes a market training task that shares an entity and an overlapping time window with a development, test or FinSearchComp task, mainly to protect FinSearchComp, whose outside tasks do not follow our split. One FinSearchComp task stays out of this check, since its 184 month-end S&P 500 closes would otherwise delete every filing_reaction trajectory.
  • Base-model screening: The base model attempts each original-tier training task within 30 turns and repeats the ones it solves, and the filter keeps 10% of the tasks solved twice, within each task type. The base model already knows those tasks: if most stayed, the project could not show that the base model does badly on its training data, and the kept 10% keeps every task type covered. The hard tier skips this filter because the base model scores only 11.2% on its development tasks, which put the expected cut under 5%, and test tasks are never screened, since that would pick tasks it fails.
  • Per-task cap: The filter keeps at most 2 trajectories per task, those with the fewest steps first. The cap keeps the hard tier's two attempts per task, which gives that tier about twice the trajectories without new collection.
  • Funnel: The pipeline counts what each filter removes, which keeps the effect of every filter on the data traceable: the 11 filters take original-tier trajectories from 3,400 to 2,102; the 10 that apply take hard-tier trajectories from 3,500 to 2,717; the 7 that apply take wealth-management trajectories from 6,000 to 5,300 and machine-learning trajectories from 1,106 to 408. Base-model screening removes the most on the original tier (1,073), and the tool-error filter removes the most on the hard tier (361).

Deduplication keeps one sample per question

  • Exact dedup: Deduplication marks samples without report excerpts as duplicates when their user prompts are identical, so one prompt does not take several places in a training draw.
  • MinHash: Jaccard similarity divides the size of two sets' intersection by the size of their union, and MinHash estimates it quickly; deduplication marks samples without report excerpts as near-duplicates at an estimate of at least 0.9 over 5-grams, so copies with small edits also count once.
  • Excerpt matching: Deduplication treats FinQA, TAT-QA, DianJin, BizBench and synthetic samples as one question only when their normalized questions match and the Jaccard similarity of their excerpts' number sets is at least 0.5, because MinHash over whole prompts marks 2,202 of 3,515 FinQA samples as duplicates by treating different questions on one excerpt as copies.
  • Source priority: Deduplication keeps the first sample of each group, ranking FinQA and TAT-QA first, Tülu 3 next and synthetic document QA last, because the same FinQA question also appears in DianJin and BizBench and FinQA's own solution comes from its standard program. Synthetic document QA ranks last so that a duplicate removes only the synthetic sample and the non-synthetic pool stays the same with or without synthetic data, the two sides of the ablation above.

Mixing builds each single-turn training set

  • Ratio mixing: Each run draws 100,000 samples from a finance pool of 143,442 and the general pool at its own ratio, and the fixed sample count means runs differ in composition, not in how many samples they train on.
  • Source cap: Each run samples finance sources in proportion to their size, so runs differ only in the finance-to-general ratio, and caps a source at 40% of the finance part, so one large source cannot fill it.
  • Nested sampling: A salted hash orders each source, so a smaller draw nests inside a larger one and two runs differ only in the extra samples, which removes one layer of sampling difference from their comparison.

The data snapshot fixes the data, so programs can compute and recheck every answer

  • SQLite snapshot: One database file stores daily prices of 565 securities with 35,727 splits and dividends, 68 FRED macroeconomic series and the SEC XBRL filings of 516 companies. Live data would change, so only a fixed snapshot lets a program compute each answer and grade each task.
  • Point-in-time vintage: The snapshot stores each FRED series as published on its cutoff date, without later revisions, so a task's answer is what could be known on that date.

The split keeps test entities and periods out of training

  • Entity split: A hash of the ticker assigns each stock to training, development or test at about 70/10/20, and filing tasks follow their company, so the market-data test measures companies the model has not seen.
  • Temporal split: Indices, ETFs (funds that trade like stocks), FX rates and FRED series split by time into 2000–2016 for training, 2017–2019 for development and 2020 onward for test, so the market-data test measures periods after the training window.
  • Limit of the split: The development set holds 47 stocks and the test set 99, and the S&P 500 list comes from 2026, so it holds only companies that survived to that year.

Task generation follows FinSearchComp's operations and adds a hard tier

  • Need for harder tasks: The official Qwen3.5-4B already scores near full marks on 11 of the 14 wealth-management task types, which mainly test calling tools by the rules, so the project needs tasks the official model also does badly on.
  • Operations from FinSearchComp: Labelling FinSearchComp's T2 and T3 tasks showed recurring operations, such as unadjusted prices, the Nth trading day after a date, threshold scans, period extremes, monthly resampling, maximum drawdown and rolling standard deviation, and the generator builds task types from them because the benchmark's difficulty comes from many periods of data, price adjustment, unit conversion and multi-step aggregation.
  • Original tier: The generator builds 17 task types of difficulty 1–3 by drawing entities and time windows, with 200 training, 20 development and 30 test tasks per task type, so training practices each of the operations above on its own.
  • Hard tier: The generator builds 8 composite task types of difficulty 4–5, because the teacher solves 99.7% of original-tier development tasks and a model trained on them would leave little room for reinforcement learning. A composite task chains operations, so one wrong step fails it, and difficulty comes from steps and conventions, not obscure data.
  • One round of hardening: The generator rewrites the 5 hard task types on which the teacher scores at least 95% on the development set, giving company names only, standard terms and extra keys, which lowers the teacher from 98/100 to 93/100 on them, because the tier needs tasks the teacher can also get wrong. This happens once, because repeated changes would tune the tasks on the development set.

Answer computation gives every task a reference a program can check

  • Computed answers: The generator computes each reference answer from the snapshot and drops candidates that invite misgrading, such as answers near a rounding boundary or dates close to a threshold, so a score does not turn on a rounding edge.
  • Key-based grading: The grader splits a reference answer into keys (a number within tolerance, a date, a text or a set) and passes a task only when every key appears correctly in the final answer, so scores need no model judge and can be recomputed. A count key can still match another small integer in the answer.

Independent verification checks answers and tools

  • Independent verification: A separate implementation in SQL and Python reads only each task's parameters and recomputes its answer, and all answers of both tiers agree, so a generator bug would show up as a disagreement instead of becoming a wrong reference behind the scores.
  • Golden policy: A scripted solver uses only the tools, one Python call and finish, and solves every task through the same loop, verification and grading as the model, which shows the tools are sufficient for each task.

The dataset holds 3,148 tasks, with sources and task types chosen on development results

  • Composition: The dataset holds 3,148 tasks: 2,350 training, 200 development and 598 test tasks. The test tasks include the 300 market-data test tasks and the 98 FinSearchComp tasks. Development tasks guide the choices and test tasks guide none, so test scores stay a fair final measure.
  • Training file: The file holds 250 tasks from each of 7 hard task types and 200 from each of rolling_vol, extreme_period and xbrl_ratio, 2,350 tasks in all. It drops the eighth hard type, div_event_study, because the official model solves 19/20 of its development tasks, which leaves no room to show a gain, and it keeps the original tier's three types the official model does worst on (2/20, 14/20, 14/20). The SFT model also uses trajectories on the other 14 original-tier task types, 2,800 tasks beyond these.
  • Development and market-data test files: The files hold 200 and 300 tasks from the same 10 task types, and no test task was picked by any model's result, so the test does not favor a model.
  • FinSearchComp file: Of the 203 Global T2 and T3 tasks, the file keeps the 98 on which the snapshot's value agrees with the official answer within tolerance, so a score does not rest on a snapshot value that disagrees with that answer.
Context management Tool interface and constraints Verification and correction

The harness in this work has three parts: context management, tool interface and constraints, and verification and correction. The description below is version 3, used on market tasks; wealth-management and machine-learning tasks use version 2, which truncates older tool results into summaries.

Context management

  • System prompt: The harness opens each task with a message that states the model's role, the task's rules and how to use the tools.
  • Append-only context: The harness never changes a message after sending it, so each request's messages are a prefix of the next request and of the stored trajectory. The stored trajectory is then exactly what the model saw at each step, and SFT and RL train on the sequence as it was sampled.
  • Tool-result cap: The harness cuts each tool result to 8,000 characters when the tool returns it and appends a note on how to ask for less, such as the next page or a shorter date range. Every market tool returns at most 7,500 characters per page, below the cap, so the model does not receive cut-off JSON.
  • Checklist (set_checklist): The model writes the steps of a request into a checklist and marks them done, the harness restates the list after every tool result, and the model may call the tool at most 20 times in a task. This mainly reduces skipped sub-tasks.
  • Step budget: The harness counts only task turns against the limit of 100 steps; checklist-only turns, a turn with a rejected finish and the 10 turns after it stay outside the count, under a hard cap of 142 turns. Checklist upkeep and redoing are actions the harness itself adds, and on long tasks they would use up the step limit.
  • Thinking-preserving chat template: A changed Qwen3.5 chat template, the rule that renders messages into model input, keeps the thinking of every assistant turn after the first user message. Under the original template a nudge, which is a user message, removed the earlier thinking from the next prompt, so the stored trajectory was no longer what the model saw.
  • Token-level logging: The harness records each turn's prompt token count, sampled tokens and their log probabilities, plus prefix_ok, a flag for whether the prompt begins with the previous prompt and its completion. RL can then use the sampled tokens and probabilities without rescoring them, and the flag exposes any turn rendered differently from how it was sampled.

Tool interface and constraints

  • Function calling: The harness describes each tool's name and arguments to the model in JSON Schema, a standard format for structured data, and the model calls tools in the native function-calling format.
  • Tool sets: The market environment offers 11 tools, wealth management 12 and machine learning 5, each count including finish, which ends a task with the answer; the full harness adds set_checklist.
  • BM25 two-step retrieval: BM25, a keyword ranking algorithm, scores a passage higher when the query's words are frequent in it and rare elsewhere, and the harness uses it alone, with no vector search or reranking. A search of the wealth-management knowledge base of fund prospectuses returns ids, titles and opening text of at most 10 passages, and the model then reads a full passage by its id.
  • Sandbox (run_python): The harness runs the model's code in bubblewrap, a Linux tool that isolates a process, with no network, a read-only file system outside a temporary directory, 30 seconds and 3 GiB.
  • Constraints: Before a write action runs, code checks its arguments against the tool schema and the business rules, refuses a violating action unexecuted and returns the reason to the model, which mainly reduces rule violations and bad arguments.

Verification and correction

  • Answer verification: On finish, the harness checks that the answer's numbers have support in tool results or the request, that every checklist item is done and that the environment's own checks pass; on market tasks a number counts as supported when a tool-result number matches it after scaling by thousands, millions, billions or percent and rounding to the answer's decimals. Unit conversions therefore pass, while numbers worked out in the model's head or recalled from memory are rejected.
  • Rejection limit: The harness rejects at most 2 finishes in a task and accepts the next one unchecked.
  • Correction messages: The harness returns the failing checks after a rejected finish and an example of a valid call after a tool error, which mainly reduces loops and exhausted step budgets.
  • Loop hint: The harness tells the model to change approach on the third identical call.
  • Nudge: The harness appends a reminder after a reply with no tool call.
  • Packing: The data builder renders market trajectories with the thinking-preserving chat template up to 32,768 tokens and wealth-management and machine-learning trajectories up to 16,384, then packs the 12,475 samples into 2,439 sequences of at most 32,768 tokens, so short samples fill each sequence's token budget and a step of 12 sequences trains on about 61 samples. The market limit is 32,768 because the median xbrl_ratio trajectory has 17,661 tokens, so 16,384 would lose over half of that task type.
  • Settings: Training fine-tunes all parameters of Qwen3.5-4B-Base for 2 epochs (two passes through the data) and 408 steps, on 6 GPUs, at a learning rate of 1e-5 that falls along a cosine curve. It starts from the Base model so that everything the model learns after pre-training comes only from this project's data.
  • Loss: Training minimizes the cross-entropy between the model's next-token prediction and the label, the standard loss for next-token prediction \(\mathcal{L} = -\frac{1}{N}\sum_{t:\, y_t \neq -100} \log p_\theta(y_t \mid x_{<t})\), where \(x_{<t}\) is the sequence before position \(t\), \(\theta\) the model weights and \(N\) the number of labeled tokens, so the model reproduces the labeled turns token by token. Training computes the loss only at labeled positions, in chunks, which leaves its value and gradients unchanged, because the model's scores for every vocabulary token at every position of a long sequence do not fit in GPU memory.
  • Labels: A label is the token itself where the model should learn and −100, which the loss ignores, everywhere else. The labels cover thinking, text and tool calls in a trajectory's assistant turns, because the model later runs under a chat template that keeps past thinking in its context, and they mask system, user and tool turns, because tools produce their own output.
  • Masked turns: Market trajectories mask a reply that drew a nudge and a turn with a rejected call but keep them in the context, because a loss there would teach the model to hand in wrong answers first, while the later correction is still learned. Wealth-management and machine-learning trajectories keep the loss on rejected turns, and the builder drops any with a nudge.
  • Malformed calls: The current data builder also masks turns with malformed calls, such as unknown tool names, because a loss there teaches wrong names; the SFT model's data predates this rule, and those turns are 0.25% of its labeled tokens.
  • Sample boundaries: Each batch tells the model where every sample in a shared sequence begins and ends, because Qwen3.5's linear-attention layers, an attention variant that carries state along the sequence, would otherwise leak one sample into the next. This cut the largest per-token loss difference from 6.3 to 0.13, which is numerical noise.

Scores and comparisons

  • Success rate: The score counts the share of tasks in the set \(T\) that pass, where \(s_t = 1\) when task \(t\) passes, so only a fully finished task earns credit. \[S = \frac{100}{|T|}\sum_{t \in T} s_t\]
  • Paired bootstrap: The comparison subtracts two models' results on the same tasks, where \(a_i\) and \(b_i\) are 100 for a correct task and 0 otherwise, and takes the 95% interval from 10,000 resamples of the \(n\) tasks. Pairing removes task difficulty from the difference, which narrows the interval; it covers task sampling only, since each test task runs once. \[\Delta = \frac{1}{n}\sum_{i=1}^{n}(b_i - a_i)\]

Single-turn SFT runs

  • Finance score: The scorer takes the first number after the last "Answer:" and marks the question correct when it is within 1% of the reference, in percent or decimal form. Every model gets the same prompt with 3 worked examples and no chat template, because the base model cannot follow chat format and scores must stay comparable. Here \(D\) is the question set, \(y_i\) the reference, \(\hat{y}_i\) the answer and \(\tau_i = 0.01|y_i|\), or 0.005 when \(y_i = 0\). \[A_{\text{fin}} = \frac{100}{|D|}\sum_{i \in D}\mathbf{1}\Big[\min_{k \in \{1,\,100,\,0.01\}}|k\hat{y}_i - y_i| \le \tau_i\Big]\]

Agent SFT model

  • Market-data test and FinSearchComp: The grader applies key-based grading from the Offline dataset tab and uses the tolerance each FinSearchComp task states.
  • State comparison (wealth management): The grader compares the final holdings, cash and trade records with the reference state and the answer's key numbers with their tolerances (amounts ±$0.01, rates ±0.1 percentage points). On a task the rules forbid, it checks that the banned trade did not run and the answer names the rule, because a task counts only when both the trades and the answer are right.
  • AUC and \(R^2\) bar (machine learning): The grader requires a submitted model that scores at most 0.015 AUC or 0.03 \(R^2\) below the model that generated the data on a hidden table. This bar demands correct data handling: on the development set a fixed pipeline passes 20 of 20 tasks with a log transform of skewed columns and 1 without it.
  • pass@1 and pass@4: The scorer computes both scores over \(T_4\), the development tasks with 4 valid attempts, where \(c_t\) of the \(n_t\) valid attempts at task \(t\) pass. \[P_1 = \frac{100}{|T_4|}\sum_{t \in T_4}\frac{c_t}{n_t}\] \[P_4 = \frac{100}{|T_4|}\sum_{t \in T_4}\mathbf{1}[c_t \ge 1]\]

not started Every value here is planned. DAPO is the next reinforcement learning (RL) method. It builds on GRPO, which samples a group of attempts at each task and scores each attempt against its group. DAPO adds the first four changes below and removes the KL penalty, an extra loss that holds the model close to a frozen copy of itself. Training will use verl's own DAPO implementation and start from a retrained SFT model.

  • Clip-Higher: Training limits how far one update may move a token's probability: the ratio of its new to its old probability may fall by at most 0.2 and rise by at most 0.28.
  • Dynamic Sampling: verl's trainer drops a group whose 8 attempts all earn the same grade, all passed or all failed, whatever their lengths, and dispatches 2 refill tasks for it, because such a group holds no pass-or-fail difference and would train only on length. The refill has no cap, so a step takes longer as more groups are dropped.
  • Token-level loss: token-mean averages the loss over all tokens directly, so the tokens of a long attempt keep their full weight.
  • Overlong reward shaping: verl's DAPO reward manager adds a length reward to the grade \(r\): 0 up to \(L_s\), then falling linearly to −1 at the budget \(L_{\max}\). An attempt that fills the budget always fails, so it totals −2, and it carries loss. Here \(L\) counts an attempt's tokens with tool results, the buffer is \(L_c = 4{,}096\) and \(L_s = L_{\max} - L_c = 24{,}576\); the budget \(L_{\max} = 28{,}672\) plus a 4,096-token prompt equals the 32,768-token SFT sequences. \[R = r + \min\Big(-\frac{L - L_s}{L_c},\ 0\Big)\]
  • Reward: The grader gives +1 for a pass and −1 otherwise, as DAPO does. With 0/1 grades the same length penalty would weigh twice as much against the gap between right and wrong.
  • No KL: Training applies no KL penalty, because with long reasoning the model is expected to move far from where it started; this also saves that copy's memory and forward pass.
  • Task selection: The retrained SFT model attempts each pool task 8 times, and selection drops tasks with 0/8 passes, keeps tasks with 1–7/8 and keeps 10% of tasks with 8/8, because a task with the same grade in all attempts gives the group comparison nothing. The kept 10% leaves some solved tasks for the model to keep practicing. If more remain, a draw within each task type, in proportion to the type's share, holds the set to an average of 93.9 tasks per type, which largely sets how many times a run passes over its tasks. The model changes during training, so a selected task can also come to be all passed or all failed, and dynamic sampling keeps dropping such groups at each step.
  • Task pool: The market part of the pool holds newly generated tasks, 200 in each of 10 task types, and none of them repeats an SFT training, development or test task.
  • Settings: Each step takes 96 tasks with 8 attempts each, in mini-batches of 24 tasks, which gives 4 updates per step; the run lasts 28 steps at a learning rate of 8.7e-7, and an attempt stops at 30 task turns.

not started The final DAPO model and the retrained SFT model will run the market-data, FinSearchComp, development, wealth-management and machine-learning sets under the SFT evaluation tab's rules, with three additions.

  • Strict grading: The strict grader adds four rules to market-data, FinSearchComp and development answers, and \(r_t = 1\) when all hold. An answer may hold at most 50 numbers outside dates. It may hold at most 40 distinct dates. Each number key must appear outside any date. On a task with candidates, the first company named must be correct and each later company key must be followed by its value. The original grader accepts a key anywhere in the answer: an audit's answers that knew no reference value, only the restated task and grids of numbers, passed 209 of 939 RL training tasks, so an RL gain under the original grader alone could not be trusted. \[S_{\text{strict}} = \frac{100}{|T|}\sum_{t \in T} s_t\, r_t\]
  • Reworded test: Rewording rewrites the 300 market-data test tasks with the same parameters and answers and lowers their 5-gram overlap with same-type training tasks from 0.77–0.99 to 0.10–0.32, so a score change shows how much a result depends on wording. \[\Delta_{\text{reword}} = S_{\text{reworded}} - S_{\text{original}}\]
  • Paired gain over the SFT model: The comparison takes \(a_i\) from the retrained SFT model and \(b_i\) from the final DAPO model on each task under the paired bootstrap of the SFT evaluation tab.
